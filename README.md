# PID Tuning Doctor

A small language model that reads a text description of a PID step response and suggests the most likely tuning fault, the evidence for it and one fix. I built it as my capstone for the Google DeepMind AI Research Foundations course, by fine-tuning Gemma 3 1B with LoRA on simulated data.

It is a learning aid for control students. It was trained only on simulated plants and should not be used to tune real or safety-critical equipment.

   **Try the demo:** [huggingface.co/spaces/timflash/pid-tuning-doctor](https://huggingface.co/spaces/timflash/pid-tuning-doctor). It shows the hand-written rule baseline and a reference checklist beside the model's answer, and warns when they disagree.

## Results

The selected model (run B, epoch 6) was scored once on two test sets. Test A uses new examples from the plants seen in training, and Test B uses three plants the model never saw.

| Model | Test A macro F1 | Test B macro F1 |
| --- | --- | --- |
| Fine-tuned Gemma 3 1B | 0.894 | 0.693 |
| Hand-written rules | 0.934 | 0.921 |
| Decision tree | 0.978 | 0.918 |
| Gemma 3 1B before fine-tuning | 0.000 | 0.000 |

Both baselines did better, clearly so on the unseen plants. Most of the model's errors come from deciding whether a settling time or ripple value is above its limit, and on the unseen plants it often reported a broken requirement as met. Student-written descriptions and real hardware have not been tested yet. The full report covers the method, the error analysis and the limitations.

## What the model sees and writes

Input, one of four sentence templates:

```
A first-order process (like a motor speed loop or small thermal system) under PID control
(Kp=1.262, Ki=16.431, Kd=0). Requirements: settle within 400 ms with at most 15% overshoot,
no more than 2 oscillation cycles, at most 2% error at the end and control ripple of at most 1.3%. ...
```

The answer it is trained to write (run B format):

```
Check:
- overshoot 28% vs limit 15%: broken
- oscillations 0 vs limit 2: met
- settling 555 ms vs limit 400 ms: broken
- end error 0.0% vs limit 2%: met
- ripple 1.0% vs limit 1.3%: met
- time at actuator limit: 355 ms (22% of the recording)
Diagnosis: Actuator saturation.
Evidence: actuator at its limit for 355 ms (22% of the recording); overshoot 28% against a 15% limit; settles at 555 ms against a 400 ms target.
Fix: The actuator can hold this target but spends long periods at its limit. Use a smaller setpoint step ...
This is a learning aid; check with your instructor if unsure.
```

The seven classes are well tuned, Kp too high, overall gain too low, Ki too low, Ki too high, Kd too high and actuator saturation.

## Data

There are 661 examples (train 377, validation 60, Test A 126, Test B 98), generated by simulating PID loops and changing one gain at a time. The training plants are a DC motor modelled on the Quanser QUBE-Servo 3 (calibrated from my QLabs measurements) and randomised first-order and second-order plants. Test B uses a nonlinear water tank, a heater with dead time and the QUBE rotary arm with a hanging pendulum. See `DATA_CARD.md` for the details.

## Repository layout

| Path | Contents |
| --- | --- |
| `generate_dataset.py` | simulates the plants, injects faults, writes the splits |
| `make_v12.py` | builds the checklist-first answers in `data_v12/` |
| `check_dataset.py` | checks every record; `--selftest` corrupts records on purpose |
| `rule_baseline.py` | hand-written rules and the decision tree baseline |
| `pid_lib.py` | training with validation-based selection, checkpoints, scoring |
| `pid_doctor_lora.ipynb` | Colab notebook used for all runs and the final test |
| `data/`, `data_v12/` | the dataset in the two answer formats |
| `dev/` | a development-only dataset (seed 0) used by the tests |
| `final_results/` | the final test predictions, scores and baseline output |
| `PROTOCOL.md` | the evaluation rules fixed before training, with revision notes |
| `CAPSTONE_LOG.md` | a log of every decision and correction |
| `FROZEN_*.sha256` | checksums of the frozen code and protocol |

## Reproducing

```
pip install numpy scikit-learn
python generate_dataset.py --seed 20261031 --test_seed 20261102   # rebuilds data/ (about 3 min, byte-identical)
python make_v12.py                                                # rebuilds data_v12/
python check_dataset.py data_v12 && python check_dataset.py --selftest data_v12
python rule_baseline.py data/test_A.json data/test_B.json        # baseline scores
```

Training runs in `pid_doctor_lora.ipynb` on a free Colab T4 GPU (about 35 minutes for run B). It needs Kaggle access to Gemma, set up as in the course's LoRA lab.
